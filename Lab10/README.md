# Лабораторная работа №10 — Многопоточное программирование (TPL)

## Вариант 8

Найти количество натуральных чисел, не превышающих **10 000 000**, которые сами являются палиндромами и чей квадрат также палиндром.

Например: `11` — палиндром, `11² = 121` — тоже палиндром, значит `11` подходит.

## Цель

Изучить библиотеку TPL (`Parallel.For`, шаблон TLS, `Interlocked`) и проанализировать масштабируемость алгоритма при изменении числа потоков.

## Теория

### Поток и задача

**Поток** (`Thread`) — наименьшая единица выполнения кода, которой управляет ОС. Каждый поток имеет свой стек (~1 МБ) и состояние, но все потоки одного процесса разделяют память. Создание потока — дорогая операция.

**Задача** (`Task`) — лёгкий объект из библиотеки TPL, описывающий **что** нужно сделать. Сам TPL решает, на каком потоке из пула `ThreadPool` запустить задачу.

### Состояние гонки и Interlocked

Если несколько потоков одновременно изменяют одну переменную (`count++`), результат непредсказуем — операция инкремента состоит из трёх шагов (чтение → +1 → запись), и контекст может переключиться в середине.

Решения:
- **`lock(obj) { ... }`** — критическая секция, в которую может войти только один поток. Надёжно, но медленно.
- **`Interlocked.Increment(ref count)`** — атомарная операция на уровне процессора. Быстрее, но работает только с одной переменной.

### Класс Parallel

Из `System.Threading.Tasks`. Распределяет итерации цикла по потокам пула:

```csharp
Parallel.For(0, N, i => DoWork(i));
```

Можно ограничить число потоков:
```csharp
var options = new ParallelOptions { MaxDegreeOfParallelism = 4 };
Parallel.For(0, N, options, i => DoWork(i));
```

### Шаблон TLS (Thread-Local Storage)

У каждого потока — свой локальный счётчик. По окончании работы потока его локальный результат атомарно прибавляется к общему. Так удаётся избежать тысяч вызовов `Interlocked` — вместо этого получаем по одному на поток.

```csharp
Parallel.For(1, N + 1, options,
    () => 0L,                                  // инициализация локальной переменной
    (i, state, local) =>                       // тело цикла
    {
        if (TestNumber(i)) local++;
        return local;
    },
    local => Interlocked.Add(ref count, local) // финализатор потока
);
```

### Закон Амдала

Общая скорость ограничена временем последовательной части задачи. Если 10% кода нельзя распараллелить — даже с бесконечным числом ядер ускорение не превысит 10×. Кроме того, есть накладные расходы на создание потоков, кэш процессора, GC и планировщик ОС, поэтому реальное время всегда отличается от идеального.

## Как работает код

### Проверка числа (`TestNumber`)

```csharp
static bool IsPalindrome(long n)
{
    string s = n.ToString();
    int i = 0, j = s.Length - 1;
    while (i < j)
    {
        if (s[i] != s[j]) return false;
        i++; j--;
    }
    return true;
}

static bool TestNumber(int n)
{
    if (!IsPalindrome(n)) return false;
    long sqr = (long)n * n;
    return IsPalindrome(sqr);
}
```

Число превращается в строку, сравниваются симметричные символы. Квадрат `n²` для `n` до 10 000 000 не превышает `10¹⁴` — помещается в `long`.

### Последовательный замер

```csharp
Stopwatch sw = Stopwatch.StartNew();
long result = SerialCount();   // обычный for от 1 до 10_000_000
sw.Stop();
long serialTime = sw.ElapsedMilliseconds;
```

### Параллельный замер с лимитом потоков

```csharp
long ParallelCount(int maxThreads)
{
    long count = 0;
    var options = new ParallelOptions { MaxDegreeOfParallelism = maxThreads };

    Parallel.For(1, LIMIT + 1, options,
        () => 0L,
        (i, state, localSum) =>
        {
            if (TestNumber(i)) localSum++;
            return localSum;
        },
        localSum => Interlocked.Add(ref count, localSum)
    );
    return count;
}
```

Метод вызывается в цикле для каждого значения из набора `{1, 2, 4, 8, 12, 16}`.

### Идеальное ускорение

```csharp
if (k == 0) baseTime = time;       // время при 1 потоке — основа
long ideal = baseTime / threads;   // идеал: время / число потоков
```

Идеальное время для T потоков — это время одного потока, делённое на T. На практике из-за накладных расходов реальное время всегда выше идеального.

### Запуск в фоне

Чтобы форма не зависала во время вычислений (10 миллионов проверок занимают много секунд), все замеры запускаются через `Task.Run(...)`, а обновление UI — через `Invoke`:

```csharp
await Task.Run(() => { ... });
```

### Вывод результата

- В `txtLog` — таблица: число потоков, реальное время, идеальное время, найденное количество.
- В `chart` — две линии: фактическое время (синяя сплошная) и идеальное ускорение (оранжевая пунктирная). Точка пересечения / расхождения показывает **предел масштабируемости**.

1. Открыть `Lab10.sln` в Visual Studio 2022.
2. Собрать проект (`Ctrl+Shift+B`).

## Анализ масштабируемости

На графике видно:
- При увеличении числа потоков время убывает, но **не пропорционально** идеальной линии.
- После достижения количества потоков, равного числу физических ядер процессора, дальнейшее увеличение либо почти не даёт прироста, либо даже ухудшает результат (расходы на переключение контекста, конкуренция за кэш).

Это и есть **предел масштабируемости** — точка, после которой добавлять потоки бессмысленно.
